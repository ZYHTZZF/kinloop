# 功能4「回忆触发」详细实现规划与影响评估

根据多人协作原则与项目PRD要求，为了在不影响主干逻辑、不引发代码冲突的前提下实现“回忆触发”功能，特制定本开发规划。请您在审阅无误后授权，我再进行实际的代码修改。

## 一、 效果演示（改动后用户能看到什么）

### 1. 触发时机
当用户（如长辈或子女）在聊天框中收到或发送了一条包含**往事特征词**（如：“老地方”、“上次一起”、“记得吗”、“以前”）或**具体记忆锚点**（如：“红烧肉”、“王阿姨”）的消息时。

### 2. 视觉效果
- **展示位置**：在对应的聊天气泡**正下方**，出现一个轻量级的“消息辅助区”。
- **UI样式**：不使用突兀的强提醒，而是采用类似微信/系统轻提示的柔和卡片。复用当前项目现有的背景色（如 `var(--surface-color)` 或偏淡的底色）、圆角和字体大小。
- **展示内容**：例如，气泡下方出现一行带小图标的灰色小字：
  `💡 提到老地方了，你们上次去是在去年中秋节（点击查看提及的记忆）`
- **操作反馈**：用户可以点击该提示，展开查看一段简短的回忆摘要。看完后可以关闭，完全不影响正常的聊天视线和历史消息。

## 二、 运行原理（底层是怎么跑通的）

整个功能的实现采用**“旁路监听 + 独立服务”**的解耦架构，最大程度保护现有的聊天主骨架：

1. **消息监听（前端）**：
   - 前端增加一个独立的 Hook（例如 `useMemoryTrigger`），它只关心最新出现的聊天消息。
   - 当有新消息上屏时，前端静默向后端发起一个异步请求检查。由于不阻塞界面渲染，用户的聊天体验毫无卡顿变形。

2. **意图与记忆匹配（后端）**：
   - 后端新增一个独立的 `/api/memories/trigger` 接口。
   - 收到消息文本后，后端将其传入一个专用的 Service：结合大模型的轻量级理解（判断是否涉及回忆），并在 `memory_entries` 数据库表中进行关键词/语义检索。
   - 如果找到高度相关的历史记忆，则组装成一条“回忆提示”返回给前端；如果没有，返回空，前端什么也不显示。

3. **辅助区渲染（前端）**：
   - 前端在每条消息体下方留出一个统一的**「消息辅助容器 (MessageAuxArea)」**（这也是为了兼容功能3长消息摘要、功能5破圈解释）。
   - 如果对应消息的 `messageId` 存在后端返回的回忆触发数据，则在该容器内渲染出回忆卡片。

## 四、 潜在影响与规避方案

1. **与功能3、功能5同学的冲突风险（前端容器共用）**：
   - *规避方案*：我此次提取出统一的 `MessageAuxArea` 组件空壳，大家可以在里面基于不同类型 (`type: 'memory' | 'summary' | 'explain'`) 进行插拔式渲染。我在 PRD 层面上帮大家把占位做好了，后续他们加功能只需在此空壳内补充即可，不会反复修改 `ChatMessage` 导致冲突。
2. **样式风格不统一风险**：
   - *规避方案*：UI 完全采用内联现有 css module 的做法，引用诸如 `var(--text-secondary)` 等当前主题变量。不引入新依赖，不自行实现弹窗，只在一行文本内轻量级展现。
3. **接口请求性能风险**：
   - *规避方案*：前端对消息进行 Debounce(防抖) 处理，且只有长文本或特定条件下才会去发请求，不会每次输入单字都调 AI 和数据库。
