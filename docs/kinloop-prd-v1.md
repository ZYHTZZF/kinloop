# Kinloop V1.0 (MVP) 正式 PRD

## 1. 产品概述

### 1.1 产品定位
Kinloop 是一个面向“长辈 + 家人”的家庭关怀空间。

它不是普通聊天工具，不是家属监控面板，也不是医疗诊断产品。

Kinloop 解决的是三类核心问题：

1. 长辈想表达，但现有数字产品操作门槛高、反馈慢、陪伴感弱。
2. 家人想关心，但不知道现在值不值得联系、该怎么联系、联系后如何持续跟进。
3. 重要互动很容易散落在碎片聊天里，既无法形成持续判断，也无法沉淀成家庭记忆。

### 1.2 核心价值
1. 长辈端：通过 `AI 常驻 + 语音主入口 + 首页直接可见的家人真实来信`，降低表达门槛。
2. 家人端：通过 `今天` 工作台，把信息转成判断和行动，而不是堆成聊天流。
3. 双端共享：把有意义的图片、语音、文字轻量沉淀为共同回忆。
4. 家庭协作：通过 Circle of Care、家庭码与权限策略实现“有边界的协作”。

### 1.3 非目标
1. 不做完整社交聊天平台。
2. 不做医疗诊断与医疗建议系统。
3. 不做复杂的云端多端同步系统。
4. 不做重型后台、运营系统、复杂会员体系。
5. 不做过早的精细回忆治理与高级编辑。

### 1.4 版本范围
#### MVP 必做
1. 长辈端首页：AI 常驻区 + 家人会话带 + 固定语音按钮。
2. 长辈端联络页、单个家人会话页、回忆页、求助页。
3. 家人端今天页、状态与回访页、聊天页、回忆页、协作页。
4. 双端共享回忆时间线。
5. 消息旁加入回忆。
6. 长辈通过 AI 代发消息。
7. 长辈通过 AI 加入回忆。
8. `Pulse`、`FollowupRecord`、`Alert` 基础闭环。
9. 家庭码加入与基础 Circle of Care。
10. 本地数据库 + 本地 API 跑通核心流程。

#### P1 应做
1. 回忆条目补充编辑与人物标签。
2. 更细的角色权限模板。
3. 家人端更丰富的趋势与连续观察。
4. 更自然的 AI 回复草拟与上下文理解。
5. 更细的提醒与接力策略。

#### P2 可扩展
1. 多设备同步与云端部署。
2. 真实推送、短信、电话服务接入。
3. 高级回忆篇章化。
4. 社区或机构协作扩展。
5. 真实 AI API 接入和模型策略优化。

### 1.5 技术假设与实现约束
1. 当前阶段采用“本地优先”方案。
2. 前端形态为 Web 应用。
3. 后端采用本地 API。
4. 数据库存储采用本地 SQLite 思路。
5. AI 能力先预留接口与占位字段，API key 暂不接入。
6. 允许使用 mock 返回支撑流程验证。
7. 不默认依赖复杂云能力、实时推送、分布式任务系统、多设备同步。

## 2. 用户与场景

### 2.1 长辈用户
1. 数字设备使用能力有限，不擅长层级复杂的 App。
2. 更适合“看到真实内容 + 直接说话”，不适合频繁打字和切模块。
3. 需要稳定陪伴感，而不是偶发通知。
4. 在表达情绪、回忆往事、身体不适时，更愿意先对一个持续在场的对象开口。

### 2.2 家人用户
1. 希望知道长辈今天怎么样，但不希望产品显得像监控。
2. 希望快速判断是否该联系、怎样联系。
3. 需要和其他家人协作，但又不想所有私聊都被共享。
4. 希望把有意义的互动留存下来，不只是聊完就过去。

### 2.3 高频场景
1. 家人发来一条语音和一张照片，长辈首页直接看到并听到。
2. 长辈点进和某个家人的会话，通过 AI 口述回复。
3. 长辈或家人把一段照片、语音、文字加入回忆。
4. 家人查看今天状态，判断是否要联系。
5. 家人完成一次电话回访后，留下回访记录。
6. 家庭成员通过家庭码加入并接力跟进。

### 2.4 高风险场景
1. 长辈突然身体不适。
2. 长辈触发 SOS。
3. 长辈误触求助。
4. 长辈与某位家人的私聊内容被其他家人看到。
5. 家人端误把状态系统做成监控系统。
6. AI 让长辈分不清是在和 AI 说话，还是在和子女说话。

## 3. 产品原则

1. `AI 常驻优先`
   AI 是长辈端基础设施，不是单独功能页。
2. `表达优先于操作`
   长辈优先通过说来完成聊天、导航、回忆加入、求助。
3. `真实内容优先于摘要`
   长辈首页尽量展示家人发来的真实内容，而不是系统总结。
4. `一人一框优先于一消息一框`
   长辈首页展示的是“会话”，不是“消息瀑布流”。
5. `默认静止，手动闭环`
   家人会话带默认静止，由长辈手动左右滑动，形成闭环式浏览，不自动轮播。
6. `逐条消费，逐条已读`
   不能因进入会话页而把全部未读内容一次性清空。
7. `回忆通过显式加入产生`
   回忆不是系统自动乱抓，必须由用户点击或 AI 协助确认加入。
8. `协作必须有边界`
   聊天、状态、回忆、求助分层可见，不默认全量共享。
9. `紧急事件必须闭环`
   求助必须有触发、通知、接单、处理、关闭的完整链路。

3. `回忆`

**AI 的持续在场 + 首页直接可见的家人真实内容。**

底部导航：

1. `今天`
2. `聊天`
3. `回忆`

1. `FamilySpace`

## 5. 长辈端 PRD

### 5.1 陪伴首页

#### 页面目标
1. 长辈一进入就能开口说话。
2. 长辈一眼看到最近家人发来的真实内容。
3. 长辈能从首页自然过渡到消费消息、进入会话、发起求助。

#### 页面区块
1. 顶部轻状态区
   显示时间、日期、天气等低干扰信息。
2. AI 常驻区
   显示 AI 陪伴角色与一句轻提示，例如“想说什么就告诉我”。
3. 家人会话带
   长辈首页最重要区域。
4. 底部固定语音按钮
   全局主动作。

### 5.2 家人会话带

#### 产品定义
1. 展示单位是“一个家人对应一张卡片”。
2. 卡片代表与该家人的一个会话。
3. 首页不展示消息列表，不展示摘要流。

#### 展示规则
1. 默认静止。
2. 手动左右滑动。
3. 形成闭环式浏览。
4. 不自动轮播。
5. 可露出后一张卡片边缘，提示后面还有内容。

#### 排序规则
按 `lastMeaningfulActivityAt` 倒序排列。

含义：最近一次“有效互动”时间，而不是任何低价值动作。

有效互动包括：
1. 家人发送有效消息。
2. 长辈消费某条消息。
3. 长辈给该家人回复。
4. 该会话新增回忆加入行为。

不计入有效互动：
1. 低信息量“嗯/好/收到”。
2. 系统自动提示。
3. 发送失败消息。
4. 未接通或未完成动作。

#### 单张卡片字段
| 字段 | 说明 |
|---|---|
| avatar | 家人头像 |
| displayName | 家人称呼 |
| primaryContentType | 当前主内容类型 |
| primaryContent | 当前主内容展示体 |
| unreadSummary | 其他未消费内容汇总 |
| unreadCount | 当前仍未消费消息数 |
| lastMeaningfulActivityAt | 最近有效互动时间 |
| statusDot | 是否存在未消费内容 |

#### 主内容抽取规则
原则：展示“最新且最易理解的真实内容”。

抽取逻辑：
1. 取该会话所有未消费消息，按时间倒序排列。
2. 先看最新一条是否属于“高信息量内容”。
3. 若是，则作为主内容。
4. 若最新一条属于“低信息量内容”，向前追溯上一条未消费消息。
5. 若上一条更有信息量，则上一条升为主内容，低信息量内容以辅助提示形式展示。
6. 若所有未消费内容都属于低信息量，则仍展示最新一条，避免漏读。

#### 低信息量内容判定
满足以下条件时，判定为低信息量：
1. 纯文本且极短。
2. 命中低语义词库，如“嗯”“好”“收到”“知道了”“行”。
3. 不含时间、地点、动作、健康、情绪等关键词。
4. 不包含图片、语音、视频等媒体。

示例：
1. “嗯” 是低信息量。
2. “吃过药吗” 不是低信息量。
3. “别出门” 不是低信息量。
4. “今晚七点到家” 不是低信息量。

#### 主内容展示规则
1. 最新有效内容是文字
   直接大字号展示原文。
2. 最新有效内容是照片
   显示照片缩略图。
3. 最新有效内容是语音
   优先显示高信度转写片段，并配大号播放按钮。
   如转写失败，则显示“发来一段语音”。

#### 折叠内容规则
除主内容外，其余未消费内容折叠为提示，例如：
1. 还有 2 张照片
2. 还有 1 条语音
3. 并回复了“好的”

#### 交互规则
1. 短按主内容
   直接消费当前主内容：
   - 语音：播放
   - 图片：查看
   - 文字：展开或朗读
2. 点击头像或名字
   进入该家人的完整会话页。
3. 长按卡片
   弹出快捷动作：
   - 打开会话
   - 回复
   - 加入回忆

#### 已读与未读规则
1. 进入会话页不会自动清空所有未读。
2. 语音必须播放后才记为 `PLAYED`。
3. 图片必须放大查看后才记为 `VIEWED`。
4. 文字必须进入可视区停留超过 1 秒才记为 `READ`。
5. 首页卡片消费主内容后，只清该条消息，随后把下一条未消费内容顶上来。
6. 只有该会话全部未消费消息都处理完，卡片红点和未读提示才消失。

### 5.3 全局语音按钮

#### 页面地位
1. 常驻于长辈端主要页面。
2. 不属于底部导航，是更高优先级主动作。

#### 行为规则
1. 点击
   进入与 AI 的语音对话。
2. 长按
   直接说命令，如：
   - 打开回忆
   - 帮我找女儿
   - 帮我回儿子
   - 我不舒服
   - 救命

#### AI 在长辈端承担的职责
1. 陪伴
2. 导航
3. 转译
4. 代发消息
5. 加入回忆
6. 辅助求助

### 5.4 联络页

#### 页面目标
1. 展示所有家人会话总入口。
2. 让长辈主动找到某位家人。

#### 页面区块
1. 家人会话列表
2. 搜索入口
3. 最近互动排序

#### 核心动作
1. 点击某位家人，进入单个会话页。
2. 通过语音说“找小儿子”，直接跳入对应会话。

#### 空状态
当前还没有家人会话，建议先去首页看看家人的来信。

### 5.5 单个家人会话页

#### 页面目标
1. 查看该家人的历史消息。
2. 继续回复。
3. 从具体内容中加入回忆。

#### 页面结构
1. 顶部
   头像、称呼、返回按钮。
   必须明确显示“当前在和谁聊天”，避免和 AI 会话混淆。
2. 中部消息流
   显示文字、语音、图片、混合消息。
   消息旁可出现 `加入回忆` 小按钮。
3. 底部
   固定语音按钮持续可用。

#### AI 代发消息流程
1. 长辈按住语音按钮说“帮我回她，说照片真好看”。
2. AI 识别当前会话对象。
3. AI 生成待发送内容。
4. 弹出确认卡片并语音复述。
5. 长辈说“发送”或点击发送。
6. 家人端收到正常消息，并标记“长辈口述，AI代发”。

#### 异常状态
1. 发送失败
   显示失败提示，并支持 AI 说“重发”。
2. 识别对象模糊
   若非当前会话语境，AI 追问确认对象。

### 5.6 回忆页

#### 页面目标
1. 浏览共同回忆时间线。
2. 回味家庭互动中的高价值内容。

#### 展示形式
1. 按时间倒序时间线展示。
2. 每条回忆卡可包含：图片、语音、文字、日期、加入人信息。

#### 核心动作
1. 浏览
2. 播放语音
3. 查看大图
4. 补充一句描述
5. 删除本人创建内容
6. 对 AI 说“把这个加到回忆里”或“放上个月的海边照片”

#### 空状态
回忆还是空的，在聊天里把美好瞬间加进来吧。

### 5.7 求助页

#### 页面目标
1. 提供清晰无歧义的帮助入口。
2. 把不同严重程度的求助分开处理。

#### 页面区块
1. 联系家人
2. 我现在不舒服
3. 紧急求助 SOS

#### 交互规则
1. 重要按钮长按 2 秒触发，防误触。
2. 长按时显示环形进度反馈。

#### SOS 语音触发规则
1. 检测到“救命”“帮帮我”等高危关键词时，不进入普通对话确认。
2. 直接进入 `SOS 倒计时触发`。
3. 系统播报：已为您触发紧急求助，5 秒后将呼叫家人，如不需要请说“取消”或点击屏幕。
4. 若取消，记录为一条中等级 `Pulse`，提示家人关注。
5. 若未取消，进入 SOS 通知链。

#### 身体不适流程
1. 触发 `Alert-Unwell`
2. 家人端今天页高亮
3. 若无人接单，30 分钟后一级提醒，2 小时后二级督办
4. 接单后需提交回访记录关闭

## 6. 家人端 PRD

### 6.1 今天页

#### 页面目标
1. 告诉家人长辈今天怎么样。
2. 告诉家人现在最适合做什么。
3. 把状态转成行动，而不是转成监控。

#### 页面区块
1. 当前状态卡
   展示今日互动、当前情绪、最近提及话题、异常关注信号。
2. 建议动作卡
   展示当前最建议执行的动作，例如发语音、打电话、稍后联系。
3. Pulse 时间流
   展示今天最重要的状态脉冲。
4. 待办提醒
   高亮未闭环的 `Alert` 或待处理 `Pulse`。

#### 空状态
长辈今天还没有动态，主动发条语音问候一下吧。

#### 异常状态
长辈端离线时，顶部显示灰色断连提示。

### 6.2 状态与回访页

#### 页面定位
作为今天页的二级深层页面，承接状态历史与回访闭环。

#### 页面内容
1. Pulse 时间线
2. FollowupRecord 列表
3. 本周互动健康度轻图表
4. 连续变化趋势

#### 阅读结构
左侧展示 `Pulse`，右侧缩进展示对应 `FollowupRecord`，形成“发现问题 -> 跟进 -> 结果”的阅读流。

#### Pulse 定义
`Pulse` 是系统或 AI 自动生成的客观动态，不是原始聊天复制。

可生成 `Pulse` 的行为：
1. AI 识别到情绪波动。
2. 长辈消费家人消息。
3. 长辈主动表达身体不适。
4. 明显活跃度异常。
5. 长辈上传或分享高价值内容。

不能生成 `Pulse` 的行为：
1. 每一句原始聊天原文。
2. 纯页面点击。
3. 无意义系统事件。

#### Pulse 严重程度
1. `LOW`
   日常动态，如“妈妈刚刚看完了你发的照片”。
2. `MEDIUM`
   需要关注，如“妈妈今天提到昨晚没睡好”。
3. `HIGH`
   轻度风险，如“妈妈表示现在有点头晕”。

#### Pulse 到建议动作的规则
1. 出现 `MEDIUM/HIGH` `Pulse` 且超过 2 小时无有效互动时，生成建议动作卡。
2. 家人点击建议动作后，跳转聊天或拨号。
3. 完成跟进后，系统引导填写 `FollowupRecord`。
4. 关联 `Pulse` 状态变为 `RESOLVED`。

#### FollowupRecord 定义
家人主动记录的一次跟进结果。

例如：
1. 已打电话
2. 已吃药
3. 观察中
4. 已送医院

### 6.3 聊天页

#### 页面目标
1. 提供家人熟悉的会话体验。
2. 允许发送文字、语音、照片等内容。
3. 让家人理解这些内容在长辈端会如何呈现。

#### 页面结构
1. 会话列表
2. 单人会话页
3. 输入与发送区

#### 发送内容
1. 文字
2. 语音
3. 照片
4. 图文组合

#### 核心动作
1. 发送消息
2. 查看送达、播放、已读状态
3. 长按消息加入回忆
4. 失败重发
5. 2 分钟内撤回

#### 双端不对称规则
1. 家人端看到标准聊天流。
2. 长辈端首页只看到该家人的一张会话卡。
3. 长辈点击后才进入完整会话。

### 6.4 回忆页

#### 页面目标
1. 浏览家庭共同回忆。
2. 补充说明、查看来源、回看上下文。

#### 页面内容
1. 时间线或按月分组流
2. 回忆详情页
3. 来源署名信息

#### 回忆详情页
显示：
1. 媒体主体
2. 描述文字
3. 时间
4. “由谁在何时加入回忆”
5. 若当前用户是来源会话参与方，则显示 `回看当时聊天`

### 6.5 协作页

#### 页面定位
Circle of Care 的轻量协同工作台，不是单纯设置页。

#### 页面区块
1. 家庭关怀接力棒
2. 当前协同任务看板
3. 成员管理与权限配置

#### 家庭关怀接力棒
展示：
1. 最近谁联系过
2. 建议谁接力
3. 一键提醒接力人

##### 建议接力人 MVP 算法
1. 计算池仅包含 `Primary` 和 `Family`。
2. 仅“有效联系”更新 `lastActivityAt`。
3. 有效联系包括：有效文字、有效语音、已接通语音、完成回访。
4. 低信息量消息、系统消息、失败消息不计入。
5. 当前正在 `HANDLING` 某条 `Alert/Pulse` 的成员暂时不纳入。
6. 最久未联系者成为建议接力人。
7. 主照护者可手动覆盖，手动覆盖 12 小时内锁定生效。

#### 当前协同任务看板
展示：
1. 待认领 `Pulse`
2. 未关闭 `Alert-Unwell`
3. 当前谁正在处理什么
4. 谁已接单、谁未接单

#### 成员管理与权限配置
1. 家庭码生成与审批
2. 角色配置
3. 紧急通知顺序排序
4. 成员详情查看

#### 空状态
1. 无待办时显示“目前没有需要跟进的异常，长辈状态平稳。”
2. 仅一位家人时，接力棒可弱化显示。

## 7. 角色与权限矩阵

| 数据对象或动作 | 主照护者 Primary | 家属成员 Family | 可信联系人 Trusted |
|---|---|---|---|
| 与本人和长辈的原始聊天 | 可见/可聊 | 可见/可聊 | 不可见 |
| 长辈与其他人的原始私聊 | 不可见 | 不可见 | 不可见 |
| 脱敏状态摘要 | 全部可见 | 全部可见 | 不可见 |
| Pulse | 全部可见 | 全部可见 | 不可见 |
| FollowupRecord | 全部可见 | 全部可见 | 不可见 |
| MemoryEntry | 全部可见 | 全部可见 | 不可见 |
| Alert-SOS | 实时通知，可接单 | 实时通知，可接单 | 兜底通知，可接单 |
| Alert-Unwell | 实时通知，可接单 | 实时通知，可接单 | 不可见 |
| 家庭成员资料 | 可管理 | 可查看 | 可查看有限信息 |
| 审批新成员 | 可执行 | 不可执行 | 不可执行 |
| 配置通知顺序 | 可执行 | 不可执行 | 不可执行 |
| 删除任意回忆 | 可执行 | 不可执行 | 不可执行 |
| 删除本人创建回忆 | 可执行 | 可执行 | 不可执行 |

### 权限补充规则
1. 任何家人都不能看到长辈与其他家人的原始私聊。
2. `Pulse` 若来自私聊内容，必须脱敏。
3. 私聊内容加入回忆时，必须二次确认“加入后家庭空间可见”。
4. `Trusted` 仅在 SOS 兜底阶段参与，不进入日常内容流。

## 8. 核心对象模型

1. `FamilySpace`
   家庭空间根对象。
2. `Member`
   家庭成员及其角色、状态、通知顺位。
3. `Conversation`
   长辈与单个家人的会话。
4. `Message`
   单条消息，支持多类型。
5. `ConversationCard`
   长辈首页聚合视图对象，由 `Conversation` 和未消费消息计算得出。
6. `MemoryEntry`
   回忆条目，支持来源追踪。
7. `Pulse`
   系统生成的状态脉冲。
8. `FollowupRecord`
   家人跟进后的闭环记录。
9. `Alert`
   求助事件。
10. `PermissionPolicy`
    权限策略对象。

## 9. 状态机与业务规则

### 9.1 Message 状态机

| 状态 | 含义 | 后续操作 |
|---|---|---|
| DRAFT | 草稿 | 发送 |
| SENDING | 发送中 | 等待结果 |
| SENT | 已到本地 API | 2 分钟内可撤回 |
| DELIVERED | 已送达长辈端 | 2 分钟内可撤回 |
| READ | 文字已阅读 | 加入回忆 |
| PLAYED | 语音已播放 | 加入回忆 |
| VIEWED | 图片已查看 | 加入回忆 |
| FAILED | 发送失败 | 重发 |
| RECALLED | 已撤回 | 不可再读 |

### 9.2 ConversationCard 规则
1. 每位家人有且仅有一张卡片。
2. 卡片由该会话下所有 `未消费消息` 聚合而成。
3. 主内容按“最新且最易理解”规则抽取。
4. 进入会话页不清空未读。
5. 每消费一条，只减少对应计数。
6. 当所有未消费消息都变成 `READ/PLAYED/VIEWED` 后，红点消失。

### 9.3 Pulse 状态机

| 状态 | 含义 |
|---|---|
| OPEN | 新生成，待观察或待跟进 |
| WATCHING | 已被查看但未形成回访 |
| RESOLVED | 已有 FollowupRecord 闭环 |

### 9.4 FollowupRecord 状态机

| 状态 | 含义 |
|---|---|
| DRAFT | 填写中 |
| SAVED | 已提交 |
| LINKED | 已关联 Pulse 或 Alert 闭环 |

### 9.5 MemoryEntry 状态机

| 状态 | 含义 |
|---|---|
| DRAFT | AI 提议中，待确认加入 |
| ACTIVE | 已加入回忆时间线 |
| SOURCE_REVOKED | 来源消息已撤回，但回忆保留 |
| SOFT_DELETED | 从时间线移除 |
| HARD_DELETED | 物理删除 |

#### 删除联动规则
1. 若来源消息在 2 分钟内撤回，且该回忆未被二次查看或补充，则可级联硬删除。
2. 若回忆已被查看或补充，则不自动删除，改为 `SOURCE_REVOKED`。
3. 在回忆页删除，只移除回忆，不影响原聊天记录。

### 9.6 Alert 状态机

| 状态 | 含义 |
|---|---|
| TRIGGERED | 已触发 |
| COUNTDOWN | SOS 倒计时中 |
| NOTIFYING | 正在通知 |
| HANDLING | 已有人接单处理 |
| RESOLVED | 已关闭并记录结果 |
| CANCELED | 倒计时内取消 |

### 9.7 家庭码邀请状态机

| 状态 | 含义 |
|---|---|
| ACTIVE | 已生成，可加入 |
| PENDING | 已申请，待审批 |
| APPROVED | 已通过，成员加入 |
| REJECTED | 被拒绝 |
| EXPIRED | 已过期 |

## 11. MVP 范围与分期

### MVP 必做闭环
1. 家人发消息 -> 长辈首页会话带看到真实内容 -> 长辈点进会话 -> AI 代发回复。
2. 长辈表达或消费内容 -> 生成 `Pulse` -> 家人今天页看到 -> 家人跟进 -> 形成 `FollowupRecord`。
3. 任一方显式加入回忆 -> 双端时间线可见。
4. 长辈触发求助 -> 家人接单 -> 关闭并记录结果。
5. 家庭码加入 -> 成员进入协作圈 -> 接力逻辑成立。

### P1
1. 更丰富的回忆编辑。
2. 更智能的接力算法。
3. 更细权限。
4. 更完整趋势视图。

### P2
1. 云同步。
2. 真正短信、电话、推送接入。
3. 外部机构协作。
4. 真实 AI 模型上线。

## 12. 风险与设计决策

### 12.1 认知负担风险
风险：老人端太像消息流或工具盘。

决策：首页只保留 AI 常驻 + 会话带 + 大语音按钮。

### 12.2 监控感风险
风险：家人端像监控仪表盘。

决策：`Pulse` 只展示可行动状态，不展示完整私聊原文。

### 12.3 AI 对象混淆风险
风险：长辈分不清在和 AI 说还是在和子女说。

决策：AI 对话区与家人会话页强视觉区分；发送前必须复述确认。

### 12.4 私聊与共享边界风险
风险：共享回忆突破私聊边界。

决策：私聊加入回忆必须二次确认；回看原聊天仅参与方可见。

### 12.5 求助误触风险
风险：误报 SOS。

决策：按钮长按 2 秒；语音触发走 5 秒倒计时可取消；取消后保留 `Pulse` 日志。

### 12.6 协作失效风险
风险：协作页只停留在设置。

决策：加入接力棒、任务看板、接单状态与手动覆盖。

### 12.7 本地优先限制风险
风险：没有真实云端同步和推送。

决策：MVP 专注单机闭环与信息架构验证；所有对外能力用本地 API/mock 占位。

## 13. 结论

### 13.1 产品主线
Kinloop 的主线不是“聊天”，而是：
**长辈表达 -> 系统转化 -> 家人判断 -> 家庭接力 -> 共同沉淀。**

### 13.2 长辈端最核心的设计资产
**AI 的持续在场 + 首页直接可见的家人真实内容。**

### 13.3 家人端最核心的设计资产
**以“今天”为首页的关怀判断工作台。**

### 13.4 MVP 最该保住的 3 个能力
1. `长辈端 AI 常驻 + 家人会话带`
   这是整个产品最独特的入口体验。
2. `家人端 今天 + Pulse/Followup 闭环`
   这是家人端区别于普通聊天工具的价值核心。
3. `显式加入的共享回忆时间线`
   这是产品从“当下关怀”走向“长期关系资产”的关键。
